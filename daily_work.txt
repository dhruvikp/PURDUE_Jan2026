Triggers:
---------
	Trigger is a database object that automatically executed before or after a sepecific event occurs on a table.

	Events:
		- INSERT
		- UPDATE
		- DELETE

	Triggers - automatically , not manually.

 Key Characteristics:
 	- Automatically executed
 	- Associated with single table
 	- Fired on INSERT/UPDATE/DELETE
 	- Can BEFORE or AFTER an event
 	- Uses NEW and OLD Keywords
 		UPDATE - NEW  - valuse after change (OLD- value before change)
 		INSERT - OLD - Not allowed New available
 		DELETE - OLD available and NEW not available

 	- cannot accept parameters or return values
 	- Executes as part of transaction

Syntax:
	
	CREATE TRIGGER trigger_name
		BEFORE | AFTER INSERT | UPDATE | DELETE

	ON table_name
		FOR EACH ROW  --> Triggers runs for every affected row
	BEGIN
		SQL Statements;
	END

	DELIMITER;


SIGNAL SQLSTATE - Manually raise an error or warning condition in storedprocedure/trigger . 
45000 --> generic 'unhandled user-defined excetion'

Practical applictions of Triggers:
	1. Logging
	2. Data validation
	3. Audit trails
		keep track of who changed what and when
    4. Automatic data synchronization


Two types of triggers:
	1. Row - Level Trigger
		Executes once for each row affected by the DML statement.
		If statement affect N rows, trigger fire N times.

	2. Statement - level trigger
		Executes once per SQL statement, regardless of how many rows are affected

		once per statement
		DO not use FOR EACH ROW
		CAN NOT ACCES TO OLD ADN NEW
		Used for summay logging or bulk operations

	oracle
	postgresql
	sql server

	UPdate employees set salary = salary+10000, where dept=10;
	insert bulk_log values ('',New())

Can we modify Trigger in MySQL? 
	NO

DROP trigger trigger_name
create trigger again with the same name

Avoid triggers when:
	- Business logic is complex
	- Logic changes frequenty
	- Performance is critical on bulk updates
In that case:
	better to handle thorugh stored procedure.


Best practice:
1. Keep triggers simple and lightweight
2. Avoid recursive triggers
	trigger should not modify same table it is attached to
3. USE BEFORE Triggers for validation
4. Use AFTER Triggers for Logging and Auditing
5. Always log critical changes
	- Salary change
	- status udpates
	- Deletions
6. Give meaningful names to triggers

Index:
	An Index in MySQL is a data structure that improves the speed of data retrieval (SELECT queries) on a table.

	Ex:
		Index of book --> jump to a topic
		instead of reading every pages. (full table scan)



	Seperate datastructure(BBT)

		DHRUVIK --> internal referece

	MySQL directly jump to matching rows

Characteristics:
	- Improves SELECT query performance
	- Created on one or more columns
	- Stored separately from table data
	- Automatically updated when data changes
	- Uses additonal disk space
	- can slow down INSERT, UPDATE, DELETE
	- MySQL uses indexes automatically for primary key

Types of Index
	1. Non-Unique Index
		- Allows duplicate values
		- Used for faster searching
		- Most commonly used index type


	2. Unique Index
		- Ensures no duplicate values
		- Allows only one NULL
		- Enforces data integrity

		Usecase:
			- Email
			- PAN,SSN

		create unique index idx_emp_email
		on employees(email);

		-> prevents dupicate email entries
		-> faster lookups and data validation

	3. Primary Index 
		- Automaticallly created when PRIMARY KEY is defined
		- Values must be unique and NOT NULL
		- only once per table


	4. Composite index (Multi-column index)

		- Index can be created on multiple columns
		- Order of columns matters

	Ex:
		- Search by (dept_id + status)
		- Filter by (Age + salary)

		CREATE INDEX idx_dept_status
		ON employees (dept_id, status);

		Helps queris using
			- dept_id
			- dept_id + staus

		Doesn't help queries using only status column


	4. Full Text Index
		
		- Used for text searching
		- Supports natural language search
		- Works on CHAR, VARCHAR, TEXT

	ex:
		- Search employee profiels
		- Product descriptions
		- Blog content


	CREATE FULLTEXT INDEX idx_emp_name
	ON employees(emp_name);	


	5. Spatial index

		used for geographical data
		works with spatial data types (POINT, GEOMETRY)

		Ex:
			Maps
			Location based search

	CREATE SPATIAL INDEX idx_location
		ON locations(coordinates);



- MySQL doesn't support rename index
	DROP
	CREATE

Overidnexing - creating too many unnecessary indexes
	- Slower DML operations
	- Increased disk usage
	- higher maintainance cost

Note:
	Used in where order by  join

	use composite index wiesely
		- place most selective columns first
		- follow actual query patterns

Backup and restore
	Backup - Copy of database that can be used to restore the database in case of:
		- Data loss
		- hardware failure
		- Accidental DELETE/DROP
		- Corruption
		- Security attacks
		- Migration or upgrade

	Restore - Process of recovering data from backup and loading it back in MYSQL.


Types of backup
	1. Logical Backup

		Storing data as SQL statements such as:
			CREATE TABLE
			INSERT INTO

		saved in .sql file.

		mysqldump

		- Human readable
		- Portable across versions
		- slower for very large databases
		- easy to restore


	2. Physical backup	

		Physical backup copies the acutal database files from disk.

	Tools:
		- MySQL enterprise backup
		- File system copy 

		.ibd or .frm files

	- Faster for large datasets
	- Not human readable
	- versions and OS dependent
	- More complex restore



mysqldump- command line utility used to create logical backups in MySQL

It exports:
	- Database structure
	- Data
	- INdexes
	- Constraints

	What is SP?
		- SP is precompiled collection of SQL statements, that can be stored in the database and executed as a single unit.

	SP allows us to:
		- Reuse SQL logic
		- Improve Performance
		- Encapsulate business logic inside the database.

	Key Characteristics of SP

		- SP stored inside database
		- Can accept input parameters
		- Can return output values
		- Can contains multiple SQL Statements
		- Reduce network traffic
		- Improves security by restricting direct access to tables
		- Can include control logic (IF, Loop, WHILE)


Examples:
	- Salary calculation
	- Employee onboarding
	- Order processing
	- REport generation
	- Data validation logic

What are parameters in Stored Procedure?
	Parameters are variables that allow data to be passed into or returned from stored procedure
	They makes stored procedure dynamic and reusable.

Types of parameters in MySQL
	Three types of parameters
		- IN parameter
		- OUT parameter
		- INOUT parameter

IN Parameter:
	- Used to pass values into the stored procedure
	- Default parameter type
	- Value cannot be cchanged outside the procedure


OUT Parameter:
	- Used to return a value from the stored procedure
	- Acts like a return variable
	- Value is set inside the procedure and read outside

	Ex: Returning total employees
		  Returning calculated salary

INOUT parameter:
	- Used to pass value in and return a modified value.
	- Acts like both input and output

View Processing Algorithms
	Determines how MySQL executes view query internally?

	It defines:
		- Wheter MySQL merges the view query?
		- Or creates a temporary table?
		- Or decies automatically?

	1. MERGE ALGORITHM
			- View Query is merged into the main query
			- No temporary table created
			- faster execution


	2. TEMPTABLE ALGORITHM

		- MySQL creates temporary table
		- Stores view result first
		- Query runs on temporary data.

	3. UNDEFINED Algorithm
		- MySQL decies whether to use MERGE or TEMPTABLE

Sub Query
	
	SubQuery is a query written inside another sql query.

		- Inner query --> Executed first
		- Outer Query - Uses result of inner query.

	Also known as nested query.

	Why ?
		- To break complex problems into smaller steps
		- To avoid temporary tables
		- To write readable and logical SQL
		- To derive values dynamically
		- To use query results inside another query

	Types:
		- Single-Row subquery
		- Multi-Row subquery
		- Correlated subquery
		- Subquery with exists
		- Subquery in SELECT/FROM/WHERE


		Single-row
			- Returns only one row
			- can be used along with = , > , <

		Multi-Row subquery
			- Returns multiple rows
			- Used with IN, ANY, ALL

		Correlated subquery
		
			- Innerquery depends on outer query
			- Executes once for each row
			- Uses outer query column inside subquery

		Ex: Find out employees earning more than average salary of their department?

			For each employee, subquery calculates department average
			- Comparision happens row by row
			- More powerful but slower than normal subquery


		Subquery with exists
			- Checks whether subquery returns any rows
			- Returns true or false
			- Stops execution after first match


			Ex: Find out departments that have atleast one employee

		SubQuery in select clause

			Ex. show employee name with department name using subquery

JOINs
	A Join is used to combine rows from two ore more tables based on related column.

	In our case:
		employees.dept_id
		department.dept_id

INNER JOIN
	returns only those records where matching values exist in both tables.

LEFT OUTER JOIN
	- All records from LEFT table (employees)
	- Matching records from the RIGHT table (departments)
	- NULL where no department exist

RIGHT OUTER JOIN
	- All records from the RIGHT table (departments)
	- Matching records from LEFT table (employees)
	- Null where no employee exists


FULL OUTER JOIN
	- All employees
	- All departments
	- Matches where available
	- Null where no match exist

	MySQL doesn't support FULL OUTER JOIN directly

	We simulate it using LEFT JOIN + RIGHT JOIN + UNION


Cartesian JOIN (CROSS JOIN)
	Produce every possible combination of rows from both tables.

	Ex:
		empyees table = 10 rows
		depatments table = 4 rows

		Result = 40 rows
	= No join condition used
	- Each employees is paird with every department
	- Usually not desired in real applications

	- Relationship between tables

		- ALl tables are connected using primary keys and foreign keys

	- Data Integrity
		RDBMS enforces rules that ensures
			- No duplicate records
			- No missing mandatory values
			- No invalid relationships

		Protects data quality at db level

	- ACID compliance

		A - Atomicity - All or nothing

		C - Consistency - Valid state before and after	
		I - Isolation - Transactions do not interfere
		D - Durability - Data is permanenty saved

	- Security and Access control

		Ensures only authorized users can access or modify data.

	- Scalability and Reliability
		- Handles large volumes of data
		- Supports multiple concurrent users
		- Provide backup and recovery mechanisms

	ERD - Entity Relationship Diagram 

		Visual representation of a database design that shows:
			- What data is stored (entities)
			- How data is described (attributes)
			- How data is connected (relationships)

		ERD Acts as blueprint of database before it is implemented.

	Why ?
		- Helps to udnerstand business requirements
		- Improves communication between technical and non-technical stakeholders
		- Reduce design errors
		- Serves as documentation for database structure
		- Helps convert business logic into database schema.


Key components of ERD
	1. Entity
		Real world object or concept that has independent existence and about which data is stored in database

		Each entity ususally becomes table in database


		Types of entity:
			a. Strong entity

				Entity that 
					- exist independently
					- Has its own primary key
					- Doesn't depend on any other entity for its existance


			b. weak entity

				Entity that
					- Cannot exist independently
					- Depends on a strong entity for its existance
					- Doesn't have a complete primary key on its own

				Example:
					- OrderItem (depends on Order)
					- Invoice LI (depends on Invoice)

			c. associative entity
				Entity created to:
					- Resolve relationships as a table
					- contains foreign keys from participating entities
					- may contains additional attributes

				Enrollment
				Student - Course


				Student 		course			student_course(join table)
												student_id course_id

				Order_Product



	2. Attribute
		An Attribute is a property or characteristics that describes an entity

		Examples:
			- StudentName
			- EmployeeSalary
			- ProductPrice


		Attribute becomes columns in table

		1. Simple Attribute
			- Atomic
			- Indivisible
			- Can not be brokendown further

		Ex:
			Age, Salary, Gender

		2. Composite Attribute
			Can be broken down into smaller sub-attributes

			Name --> First Name, Last Name
			Address --> Street, City, State, ZIP

		3. Derived Attribute
			- Calculated from another attributes
			- Usually not stored physically

		Ex: Age (derived from DOB)
			- Total Amount (Derived from qty * price)

		4. Multivalued attribute
			- Hold multiple values for single entity

			Ex. Phonenumbers (1,2,3)
			- email_add(..,..,..)
			- skills(..,..,..,)

			Multiple attribute handling as separate table

		5. Single valued atttribe
			- Exactly one value for an entity

			Ex: 
				DOB
				EmpId
				SSN


	3. Relationship

		Cardinality
			- Number of instances of one entity associated with another

			1. One-One-One (1:1)

				One entity is related exlactly one instance of another entity

				Person - Passport
				User - Profile


			- Often merged into single table 

			2. One-To-Many (1:M)
				One entity is related to multiple instances of another entity

				customer - Orders

				Department - Employees

				This is most common used

			- Often managed as separate columns as FK constraint

			3. Many-to-Many(M:M)
				Multiple instances of one entity is associated with multiple instances of another entity

				Student <-> Course
				Product <-> Order

			- Often manged as separate join table


ER Models
	
	ER models are created different level of abstraction during database design

	Each level represent specific purpose and audiance:

	1. Conceptual ER Model
		High level business view of data

		Focus
			- what data is needed, and how it stored



	2. Logical ER Model

			Detailed, structured view of data, while independent of any specific DBMS

			converts business req -> structured data model
			Defines Attributes, keys, relationships

			Still DBMS Independent

	3. Physical ER Model	

			Actual implementaiton of db - specific DBMS

		It transplate model attribute, entity --> table, columns and constraints in db
